> **版本变更**
> - v1.0 → 推翻"离线可玩"假设：没有 LLM 游戏不可运行，不做降级。

## 1. Steam 目标反推出的架构要求（v1.2 新增，最重要）

Steam 上的两种模型供给方式，必须在架构里**现在就留好口子**，否则后期要动地基：

| 模式 | 形态 | 对架构的硬要求 |
|---|---|---|
| A. 玩家自填 LLM API（BYOK） | 桌面客户端直连玩家自己的模型服务 | 密钥存本地（OS 凭据库/加密文件），不经过我们的服务器；单机流程不依赖我方后端 |
| B. 平台代调（Steam 用户 → 我们的服务 → 模型） | 客户端带 Steam 票据请求中转 | 凭据抽象成"来源"，代码不写死 BYOK；中转层是**加法**而非重写 |

由此得出 5 条**现在就必须遵守**的设计约束：

1. **核层（`src/core`）是纯逻辑，零 IO** —— 不 import `fs` / `http` / `ws`，模型与索引由外部注入。这样它能被 Node 服务、Electron 主进程、甚至客户端 Worker 直接复用；上架时把"我们的服务器"换成"本地进程"不需要重写判定逻辑。
2. **凭据抽象** —— `AiCredential = {kind:'byok', baseURL, apiKey, model} | {kind:'platform', ticket}`。MVP 只实现 `byok`，但调用方只依赖接口，模式 B 是新增一个实现。
3. **单机不依赖我方云端** —— 会话存在本地（浏览器 `localStorage` / 桌面端 `userData`），不引入账号、不引入云存档。多人（后期）才需要服务端。
4. **零外部 CDN** —— 字体、脚本、样式全部本地打包。Steam 客户端离线启动、国内网络环境都不允许依赖外部域名。
5. **协议类型共享** —— 前后端共用 `src/shared/protocol.ts`。上架前会加大量 UI 与成就系统，协议漂移是最难查的一类 bug。

> 这 5 条不增加 MVP 的工作量，只约束"代码往哪儿放"。反过来，如果 M1 就把 UI 逻辑写进服务端、把密钥硬编码在请求里，后面 Steam 化就得重写。

## 2. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 运行时 | **Node.js 22 LTS** | 原生支持 `.ts` 类型擦除 → 服务端**零编译**；单进程承载 HTTP + WS |
| 语言 | **TypeScript（全栈）** | 协议/证据包/DTO 都是结构化数据，类型能挡住一整类"字段漏改"bug；上架前代码量会翻倍 |
| HTTP | express 4 | 静态资源 + 少量 REST |
| 实时 | ws 8 | 需求指定 WS，协议自控 |
| 前端 | **Vite + 原生 DOM（不用 React）** ⚑ | Vite 给打包产物（Electron 可直接加载 `dist`）与 HMR；原生 DOM 保持 M1 简单。React 后续可增量化引入，因为 Vite 已在位 |
| 存储 | 进程内存 + JSON 快照（服务端）/ localStorage（客户端） | 无账号系统；接口已抽象 |
| LLM | **OpenAI 兼容 `/chat/completions`**（必需） | 一次适配覆盖 DeepSeek/通义/Kimi/智谱/vLLM；BYOK 必须 |
| 百科 | 可插拔 provider，默认 `local` | 百度百科无公开 API；维基可达性不可控 |
| 测试 | `node --test`（直接跑 `.ts`） | 零依赖，Node 22 原生支持 |

**为什么改判不用 React**：Steam 上架真正需要的是"能打包成桌面应用"，这件事 Vite 已经解决；React 解决的是"UI 复杂度"，而 M1 只有 4 个视图。先上 Vite（拿走打包与 HMR），把 React 留成可选增量——比一次性上重型框架、再在 Steam 打包阶段返工要稳。

### 5.2 会话与回答记录

```ts
type SoloSession = {
  id: string; targetId: string;        // ★ targetId 永不下行
  difficulty: 1|2|3; dynasty: string|null;
  turnsLeft: number; status: 'playing'|'won'|'revealed';
  history: AnswerRecord[];
  createdAt: number; updatedAt: number;
};

type AnswerRecord = {
  seq: number; question: string;
  query: { attr: Attr; value: string|number|boolean } | null;
  verdict: 'yes'|'no'|'unknown';
  text: string;
  basis: 'index'|'evidence'|'subjective'|'fallback';
  calls: number; ms: number;
  invalid?: 'suspicious'|'cheat';      // 无效问：不扣次数、不换回合
};
```

`basis`/`calls` **对局中不下发**，仅揭晓后在"对局回顾"展示（防反推）。

受控属性 `Attr`：`dynasty | gender | emperor | role | birthplace | birthEra | nameLength | nameContains | lifespan | alive | nationality | event | other`

## 6. 判定链路

**知识优先**：模型用自己的历史知识回答，参考资料只在它拿不准时用来校对。

早期的"模型只做翻译、判定全靠索引字段"方案被否决——那会把一个懂历史的模型压成只能回答十来个字段的表单，问"他杀过韩信吗"也只会回"无法判断"。

```
提问
 ├─ Precheck        纯代码：空/超长/控制字符 → 提示改法，不扣次数（不做意图审查）
 ├─ 非二元问句检查    选择句 / 开放句 → 直接给改法，0 调用、不扣次数
 ├─ 主观短路         伟大/厉害… → 固定话术，0 调用
 └─ 模型作答         一次调用 = 理解 + 作答（人物资料作校对锚点）
      └─ 朝代复算     唯一强制覆盖项：严格史学分期由索引裁定
```

| 问句类型 | 模型调用 | 实测延迟 |
|---|---|---|
| 常规问题（含长尾知识） | 1 | 1.2–3.3s |
| 主观评价 / 问法不对 / 空或超长 | 0 | < 10ms |
| 模型输出非法 JSON | 2（重试 1 次） | 失败不计次数 |

**为什么朝代必须由代码复算**：模型的默认认知是"曹操是三国人物"，而本游戏按史学分期要求答"否"（见 6.2）。复算用的朝代必须取自**问句本身**，不能取模型返回的 `value`——那个值指的是"人物所属朝代"，直接比对会把"他是唐朝人吗"的答案反过来（刘邦→西汉→误判为是）。

### 6.0 混合判定的边界

| 问题 | 谁说了算 |
|---|---|
| 朝代 | 索引（严格分期，可复现） |
| 其他一切客观事实 | 模型知识 |
| 资料与模型冲突（非朝代） | 以模型为准，资料只作校对 |
| 双方都不确定 | unknown |

### 6.1 回答模式

开局时选择，写进会话，整局不可变（中途改会破坏难度一致性）。

| 模式 | 输出 | 成本 |
|---|---|---|
| `strict` 精确 | 只给 `是 / 否 / 无法判断` | 0 额外调用（模板表达） |
| `guided` 解说 | 答案 + 一句**判定口径说明** | 0 额外调用（确定性说明表） |

解说模式的关键约束：说明只解释"这个问法是怎么判的"，**不得透露未被问到的信息**。

- 允许：「宋」包含北宋与南宋 / 以是否正式称帝为准，追尊不算
- 禁止：他享年 61 岁（那是另一个问题的答案）
- 硬保险：说明文本若包含目标人物名或别名，直接丢弃

说明来源分两级：判定层给出的"为什么不确定"（如"生卒年记载不全"）优先，其次是按属性查口径表。全部确定性生成，不额外调模型——保证延迟稳定、口径一致。

### 6.2 严格史学分期

判定按**史学分期**，不按民间印象。典型例子：

| 人物 | 卒年 | 判为 | 问"他是三国人物吗" |
|---|---|---|---|
| 曹操 | 220 | 东汉（三国始于同年曹丕称帝） | **否** |
| 关羽 | 220 | 东汉 | **否** |
| 周瑜 | 210 | 东汉 | **否** |
| 刘备 | 223 | 三国（221 年建蜀汉） | 是 |
| 司马懿 | 251 | 三国 | 是 |

落法有三处，缺一不可：

1. **索引数据**：`dynasty` 存严格分期；`dynastyAlt` 只放人物**实际经历过**的时期（所以曹操的 alt 里不能有三国）。
2. **提示词**：解析器"照玩家所问照抄，不按你认为正确的分期去替换"——避免模型自作聪明把三国改写成东汉。
3. **解说口径**：三国/东汉边界写进口径表，解说模式回答时一并给玩家（"按史学分期，三国起于 220 年曹丕称帝"）。

这样"答否"不会显得莫名其妙：精确模式保持纯粹，解说模式给出分期依据。

## 7. 防误伤与复盘约束（取代早期的"防作弊四层"）

这是**自我挑战型单人游戏**：玩家绕过规则只坑自己。因此不做"作弊审查"——早期的终审 AI 与判负机制已删除，省掉一次调用，也省掉一套不可复现的判罚逻辑。

保留的三件事：

| 机制 | 目的 |
|---|---|
| 服务端锁定 + DTO 白名单 | 防止误操作/扒接口提前看到答案，不是防玩家作弊 |
| 输出端去名过滤 | 模型回答里出现姓名或别称即替换为「他」，避免直接泄底 |
| 问法纠正 | 选择句/开放句给出可用的改法，比甩一句"无法判断"体面 |

多人模式（M2）的约束改为**事后可复盘**：对局记录对参与者公开，异常提问由人判断，不引入 AI 判罚。

## 8. 多人（M2，本次不实现，但接口留好）

- 房间 2–8 人；**房主 BYOK**：房主在客户端填 Key，通过 HTTPS 提交，服务端仅在房间生命周期内持有于内存，**不落盘、不写日志、不广播给其他玩家**；房间销毁即释放
- 玩家看到的只有"本轮由某某的凭据驱动"，不含任何密钥片段
- 提问预算 `clamp(人数×4, 12, 30)`，轮流提问，任意玩家可抢答（每人 2 次），首个猜中者胜
- 竞态：状态变更同步串行 + 房间级 `pending` 标记；回合超时 90s 跳过

## 10. 前端（M1）

- **首次进入即门禁**：无有效配置 → 引导页（Base URL / Key / Model / 温度 + 测试连接），通过后解锁开局
- **三态**：未配置 / 已配置 / 连接失效（遮罩 + 重试）
- **设计令牌**：宣纸 `#f4efe3`、墨 `#1c1a17`、朱 `#b1382c`、青 `#3d5a4c`；Noto Serif SC 系（本地打包或系统宋体降级）
- **移动端**：< 720px 单列、输入吸底、触控 ≥ 44px
- **揭晓前**：不渲染任何人物名，占位"？？？"
- **密钥**：仅存 `localStorage`，只在请求头发往自家后端，不进 URL、不进日志
