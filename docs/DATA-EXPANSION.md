# 人物库扩充方案

> **状态：方案留存，暂不实施（2026-10-30）**
> 当前先保 130 人的质量与字段完整度；等确实需要更大题库时再回到这份方案。
> 若要走手工路线，见 §9。

---

## 0. 结论摘要

- **瓶颈不是总数，是分布**：130 人里 L1（家喻户晓）只有 25 人，且集中在唐、宋、明、清；西晋与五代为 0，玩家选中后会静默抽到别的朝代。
- **若扩充，主力用 Wikidata**（CC0、字段结构化、可商用），CBDB 作为高质量骨架但需先解决授权。
- **不要一次性倒库**：用 `core / extended / draft` 三层池，抽样默认只从 `core` 取，自动导入的数据先落到 `extended`，审核后才升级。
- **第一步只需 30 分钟**：跑一条 SPARQL `COUNT` + 抽 20 条看政权字段覆盖率，就能判断自动导入是否值得做。

**结论**：真正影响耐玩度的是「每个朝代的 L1/L2 密度」和「空朝代」。扩到 300 人左右即可消除重复感，盲目堆到 2000 个冷门人物反而会让玩家 20 问也猜不到。

### 扩充优先级

| 优先级 | 目标 | 预计增量 |
|---|---|---|
| P0 | 填满空朝代（西晋、五代），每个 L1≥2、L2≥3 | +10 ~ 16 |
| P1 | 每个朝代 L1≥3、L2≥5 | +80 ~ 120 |
| P2 | 补强三国、隋、南北朝、蒙古、元 | +30 ~ 50 |
| P3 | 扩 L3 冷门池 | 不限 |

做到 P2 约 300 人，是性价比最高的规模。

## 2. 数据源对比

| 来源 | 规模 | 字段质量 | 许可 | 工程成本 | 定位 |
|---|---|---|---|---|---|
| **Wikidata** | 中国古代人物数千人量级（需实测） | 生卒 / 籍贯 / 职业 / 别名结构化 | **CC0，可商用** | 中 | 主力扩充 |
| **CBDB**（中国历代人物传记资料库） | 约 42–52 万条，先秦至晚清 | 姓名 / 字号 / 生卒 / 籍贯 / 朝代 / 官职最权威 | **学术授权，商用需确认** | 高 | 骨架来源 |
| 中文维基百科 | 覆盖最广 | 信息框质量参差 | CC BY-SA（需署名，衍生同源） | 高 | 冷门补充 |
| 百度百科 | 覆盖广 | 好 | **版权归百度，不可批量使用** | — | 排除 |
| LLM 生成 | 无限 | 幻觉率高（生卒、别名） | 无 | 低 | 只补主观字段 |
| 众包 | 持续增长 | 取决于贡献者 | 自定 | 中 | 长期补充 |

补充说明：

- CBDB 规模来自公开检索（浙大图书馆约 52.1 万条、CBDB 总览约 41.7 万条，统计口径不同）。它的朝代、籍贯、字号是结构化的，不需要推导；但**大量收录的是地方士绅与中低层官员**，知名度不足以支撑猜谜，且商业授权条款需单独确认。
- Wikidata 的关键属性：`P31`（人类）、`P569`/`P570`（生卒）、`P19`（出生地）、`P106`（职业）、`P27`（国籍 / 政权）、别名表。

## 3. 三层人物池设计

现有 130 人是人工核对的，质量不能因为扩充而降级。建议给 `Character` 增加来源与可信度标记：

| 层 | 来源 | 参与抽样 | 审核状态 |
|---|---|---|---|
| `core` | 现有 130 人 + 人工新增 | ✅ 默认 | 已核对 |
| `extended` | Wikidata 自动导入 + 规则推导 | ⚠️ 可配置开关 | 未逐条核对 |
| `draft` | LLM / 众包候选 | ❌ | 待审核 |

建议字段：

```ts
interface Character {
  // ...现有字段
  tier?: 'core' | 'extended';
  verified?: boolean;
  source?: string;        // 例如 wikidata:Q7071
}
```

对应改动：

1. `CharacterIndex.pick()` 增加 `tiers` 参数，默认 `['core']`；
2. 后台列表增加 `tier` / `verified` 筛选与「升为 core」操作；
3. 揭晓页可选择是否展示来源（`source`）。

这样即使自动导入出错，也不会污染玩家体验；审核通过后再升级。

## 4. 导入管道

```
SPARQL 拉取 → 字段映射 → 朝代推导 → 去重 → schema 校验 → draft JSONL → 后台审核 → 入库
```

现有 [core/schema.ts](../src/core/schema.ts) 的校验与 [data/characters.json](../data/characters.json) 的格式可以直接复用，导入器只需负责"外部字段 → Character"的映射。

### 4.1 朝代推导（核心难点）

Wikidata 没有"朝代"字段，两条路：

1. **优先 P27**（country of citizenship，如"唐朝""清朝"）直接映射到 `DYNASTIES`；
2. **缺失时用生卒年推导**：[core/dynasty.ts](../src/core/dynasty.ts) 已有完整朝代区间 `SPANS` 与 `periodsLived()`，可算出"经历过哪些时期"，再按主要活动期选主朝代。

注意边界：曹操（155–220）用"生卒覆盖"会同时命中东汉与三国。规则应是**取卒年所在时期**或**活动期重心**，不能简单取并集，否则会重现当年那次分期争议。参考 [docs/TECH-DESIGN.md](TECH-DESIGN.md) 的分期铁律与 `core/schema.ts` 中"卒于 220 年前的东汉人物不得标注三国"的校验。

### 4.2 难度分级

没有权威数据，可用的代理指标是 Wikidata 的跨语言链接数（sitelink count）：

| 跨语言链接数 | 建议难度 |
|---|---|
| > 30 | L1（入门） |
| 10 – 30 | L2（进阶） |
| < 10 | L3（考据） |

先自动分档，再人工校准 20–30 个样本。后续也可参考中文维基页面浏览量。

### 4.3 身份词映射

需要一张 `P106 (occupation) → 受控身份词` 的映射表，例如：

```
poet → 诗人
politician → 政治家
military officer → 将军
philosopher → 思想家
painter → 画家
```

现有数据里已有 43 个身份词（见后台「身份」多选），映射表约 50–100 条，一次性工作。

### 4.4 去重

后台目前只做 `id` 与 `name` 的精确查重，批量导入需要加强：

- 姓名 + 别名 + 生卒年三元组模糊匹配；
- 同一人物不同来源（Wikidata 与 CBDB）合并时保留 `source` 列表。

### 4.5 合规过滤

- 只收已故人物（`P570` 存在且逝世早于 1950，对应 `DYNASTIES` 最后一档"近代"）；
- 排除近现代政治人物（沿用现有内容规范）；
- 批量导入前用黑名单标签再过滤一次。

## 5. 工程改造清单

| 能力 | 现状 | 需要补 |
|---|---|---|
| 批量导入 | 只有导出 JSON | JSONL / CSV 导入 + **diff 预览**（新增 / 修改 / 冲突） |
| 去重 | `id`、`name` 精确查重 | 姓名 + 别名 + 生卒年模糊匹配 |
| 列表性能 | 全量返回并渲染 | 2000 人时需分页或虚拟滚动 |
| 审核状态 | 无 | `tier` / `verified` 字段 + 筛选 + 升级操作 |
| 抽样策略 | 全池 | 按 `tier` 过滤 |
| 来源追溯 | 无 | `source` 字段 + 后台展示 |

数据量影响：`characters.json` 从 48KB（130 人）到 2000 人约 750KB，服务端内存与启动无压力；后台前端需要分页。

## 8. 第一步验证（约 30 分钟）

不写导入器，先验证可行性：

**① 总量探测**

```sparql
SELECT (COUNT(DISTINCT ?p) AS ?n) WHERE {
  ?p wdt:P31 wd:Q5;
     wdt:P570 ?death.
  FILTER(?death < "1950-01-01T00:00:00Z"^^xsd:dateTime)
  ?p schema:description ?desc.
  FILTER(LANG(?desc) = "zh")
}
```

注意：这条查询会混入外国汉学家等与主题无关的人物，需要再叠加"出生地今属中国"或政权白名单约束，结果才是有效规模。

**② 政权字段覆盖率**

抽 20 条检查 `P27`（政权）是否存在：

- 覆盖率 > 70%：朝代可自动推导，自动导入可行；
- 覆盖率 < 40%：需大量依赖生卒年推导与人工确认，产出会打折扣，优先考虑 CBDB。

**③ 抽样人工评估**

看 20 条候选的知名度是否够格进 L1/L2。如果一半以上没听过，说明数据源需要更严格的知名度筛选（sitelink 阈值）。

## 9. 若不做导入：低成本替代路径

用户已决定暂不走导入，以下是用现有能力也能推进的部分：

1. **后台手工补空朝代**：西晋、五代各补 3–5 人（P0），直接消除"选了却抽到别人"的体验问题。
2. **补 L1/L2**：每个朝代挑 2–3 个家喻户晓的人物，把 L1 从 25 人提到 50 人左右。
3. **补全现有 130 人的字段**：后台「数据健康」当前报 12 条提醒（生年 / 卒年 / 籍贯缺失、别名单字或重名），补完能提升资料卡质量。
4. **调整抽样策略**：如果短期内不加人，可以让 `pick()` 在池子过小时明确报错，而不是静默跨朝代抽人（当前行为）。
